Homegames,

From a shared drawing prototype to a game framework, a hosted platform, and standalone games. Eight years of changes, traced through the repositories.

Scope of this timeline

Major technical changes, with dates and commit references. The original aim was local social games on phones people already used. The current direction is standalone games that people can run and share, including multiplayer, beyond the life of the Homegames servers.

05 / July–October 2026 · RTC integration October 3

The game host moves into a browser.

One player’s browser becomes the authoritative game host. Other players join over WebRTC, while the hosted catalog and source services still supply the game.

Game runs
In one player’s browser. Guests render scenes and send input; they do not run a second authoritative simulation.
Files live
Hosted source, assets and catalog still participate. Moving gameplay off Core happens before removing centralized content ownership.

This transition explains why “peer-to-peer gameplay” did not yet mean “no content backend.” A commit date establishes implementation work, not a deployment date.

06 / Today · October 2026

Keep the game. Host the session.

The website distributes static tools and curated games. Your projects live on your device; portable files and peer transfers let them travel without a central game repository.

Game runs
In the host browser, or an optional self-hosted Node server using the same package. The browser host must stay open; there is no automatic host migration.
Files live
Studio projects in IndexedDB; exported ZIP/HTML wherever you keep them. Recipients can save independent copies. Exports are not full Studio-history or progress backups.
Shared services
Static hosting and private signaling; optional STUN/TURN. Self-hosted HTTPS can still use homegames.link and certificate services, whose own database/queue needs remain separate.

This is how homegames.io works today. Saved games can play locally without Homegames. Automatic rooms currently end if signaling disconnects; manual pairing is a separate path and some networks still need a relay. Play and copy have separate UI flows, but joined players can currently request source through the gameplay protocol.

Evidence and limits
  • Implementation as of October 2026, some of it not yet pushed: homegamesio/scripts/build-site.js, studio-project-store.js, game-app.js; homegames-common/portable-project.js, portable-html.js, rtc-signaling.js; homegames-client/src/rtc-copy.js, rtc-manual.js; api/index.js.
  • Local audit: homegames-core/docs/local-ownership-audit.md. Remaining work includes execution isolation, play/copy permissions, workspace recovery, migration exports and release-device/network checks.

The earliest code sends a shared drawing to connected browsers. By the end of 2019, Homegames has a dashboard, separate game sessions, and a way to find the server on a local network.

  1. MAY–JULY 2018

    The repository starts; a drawing prototype follows.

    The first commit on May 12 contains a README and license. A prototype arrives in July. By July 22, a server keeps a 320 × 180 pixel buffer and broadcasts drawing changes to connected browsers over WebSocket.

    Commit evidence
    • homegames-core · ebacc4e — The earliest commit in the checked history; repository setup, not a working game.
    • homegames-core · 7fb185f — July 4: the first substantive prototype.
    • homegames-core · 6b0bf7f — July 22: “basic drawing app”; shared pixel state and drawing input.
  2. DECEMBER 30, 2018

    Send a scene instead of a screenful of pixels.

    Squisher changes from a rendered pixel grid to a description of entities: their colors, positions, and sizes. The browser draws the scene. That division between game state and browser rendering becomes a central part of Homegames.

    Commit evidence
    • homegames-core · e991517 — The serialization and rendering changes are visible in the Squisher and browser code.
  3. FEBRUARY 10, 2019

    Find the server without typing its local address.

    The homegames.link service is documented as an optional way to find a Homegames server in the same household. A server registers its local address; the service redirects a browser to it. It is a discovery helper, not a tunnel to another network.

    Commit evidence
    • homegames.link · 787c675 — README describes registration over WebSocket and lookup by public IP.
  4. DECEMBER 14, 2019

    A dashboard connects the games.

    The dashboard lists games, starts sessions on allocated ports, and tracks those sessions. A Home button provides a route back. Homegames now has a shell around the individual games.

    Commit evidence
    • homegames-core · b7acb9b — “working dashboard plus working home button.” Author date is December 14; committer date is December 24 in the replayed history.

Portable games.
Fewer dependencies.

The current local refactor packages source, media, and a player together. It also removes accounts and hosted publishing from the active workflow and adds a manual connection path that can bypass Homegames signaling.

  • A file you keep

    Export an ordinary ZIP of source and media, or one playable HTML file with the game and its runtime inside. A saved HTML game can run locally without loading Homegames.

  • A copy you share

    Send the complete project over an RTC data channel. Once received, a copy has its own life: it can be played, saved, edited in Studio, or passed on again.

  • A smaller website

    Build game pages and downloads as static files. Keep Studio projects in the browser. Remove accounts and centralized publishing from the active path.

  • A way around

    Exchange connection offers and answers manually to pair loaded players without Homegames signaling. Keep a home server as another option.

An illustration of the design,
not a live network test.

Independent of Homegames does not mean independent of the network. The host must stay open. Public STUN is optional; some networks require a TURN relay, which the manual interface does not configure. Automatic rooms currently close when signaling disconnects; they do not switch to manual pairing on their own.
