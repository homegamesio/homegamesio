How Homegames works

Play in your browser, make a game in Studio, or run a game server at home. This guide explains which option to choose, what gets saved, and how the pieces fit together.

What is Homegames?

Homegames is an open-source platform for making, publishing, and playing JavaScript games. Players use a browser; game authors use the Squish game framework. A game can run inside one browser tab or on a server shared by several players. Each connected device provides its own screen and input. Controls depend on the game: touch, mouse, keyboard, and supported gamepads are available, but a keyboard-only game still needs a keyboard.

  • Play now: open the catalog, pick a game, and choose a play mode. You do not need a developer account.
  • Make something: open Developer Studio, choose a template, and try the local preview as a guest. Follow the game-making guide to save and publish it.
  • Host at home: run the Homegames server on one computer and let other devices on your LAN connect. See self-hosting.

Multiplayer games may also offer Play offline and Download. Those start a one-player local session; whether that is fun or even playable depends on the game's rules. Games requiring the contentGenerator service cannot use the local-play/download path. The buttons available for a game reflect its capabilities.

“Play offline” still needs an initial download. Opening that button on the website fetches source and assets. Use Download ahead of time for a standalone HTML file you can reopen without the website. Test your downloaded copy before relying on it without internet access.

The version dropdown selects the published commit used by Play, Download, View Source, and a new hosted session. Joining an existing session joins the version already running there. Publishing a newer version does not update an active game or a file you downloaded.

Play together and share a session

  1. Open a multiplayer game's page and choose a published version.
  2. Start a session with Play with friends, or choose Join for an existing one. Starting a second session creates a separate game.
  3. Copy the player page's URL and send it to your friends. Keep the session open while they join. Studio's online preview also provides a share link.

The Private option hides a session from public session lists. Anyone with its link can still join; there is no invitation approval or password attached to that option.

Share codes work on the UTC date they were created and the following UTC date. This is separate from the session's lifetime: a session can end when nobody is connected or when its host restarts. Current servers normally allow about 30 seconds of observed empty time before cleanup, checked periodically; hosts can configure that grace. Spectators count as connected. There is no guaranteed reconnect window. An administrator can keep a session running while empty, but this does not make its share code permanent.

Progress, identity, and downloads

A running session is temporary. Progress survives only if the game implements saving. Local games use browser storage; clearing site data or switching browser, device, or website address can leave you without that save. A downloaded HTML file is a copy of the game, not an export of your current progress. Browser storage for local files also varies by browser. Homegames does not provide automatic account-based save synchronization.

A home server can save game data on disk. A server with disk saves disabled can send saves to connected browsers instead; restoring them also requires the launch flow to supply the saved data. Do not assume that reopening any hosted join link restores an old game. See the saving reference for the authoring contract.

Your in-game player ID identifies a participant in a session, not a permanent account or reserved seat. Games decide how to handle people leaving and returning.

When play does not work

  • Invalid or expired share link: return to the game page and join a current session, or ask its creator for a fresh session link.
  • Disconnected / connection error: the session may have ended, the server may be unavailable, or the network may block its WebSocket connection. Reload the game page to check available sessions.
  • A game starts but no tab opens: allow the site's game tab or use the “Your game is ready” link shown on the game page.
  • “One session at a time”: session creation is limited to one request per 30 seconds per public IP. People sharing a connection share that limit. Join an existing session or wait for the countdown.
  • No sound: click, tap, or press a key in the game to unlock browser audio. Check the device volume and, on a home server, your sound setting.
  • No controls on a phone: check the game's instructions and source. Keyboard and controller support are implemented by each game.
  • Report a game issue: include its name, selected version, play mode, device/browser, and what you did before the problem. The game page has a report form.

Games describe a scene tree

A game exports a JavaScript class from index.js. It builds a tree of Shape, Text, and Asset nodes and returns its roots from getLayers(). Most games use a 0–100 coordinate plane with a declared aspect ratio. The framework handles drawing the scene and delivering input.

When game code changes a node, it notifies the framework. In a hosted session, one game instance receives input from every connected player and produces the visual state for each screen. playerIds can select which players see a node, but authors must account for spectator and fallback frames when designing hidden-information games. The multiplayer guide explains those limits.

Squish: from game state to screen

Squish serializes the scene into binary frames containing coordinates, text, colors, and asset references. The browser's homegames-client decodes those frames and renders to a canvas. Images, sounds, and fonts arrive in separate asset bundles. Hosted input travels back as JSON messages tagged with the connection's player ID.

A game pins a Squish version in its import and metadata().squishVersion. Both the server and the browser bundle must support it. An older version is supported only while that deployment includes it; an unknown-version fallback is not a compatibility guarantee. The tutorial uses squish-142.

Where games run

Local sessions

The browser loads the game's CommonJS files, creates the game instance, runs its Squish serializer, and renders the result in the same tab. No game server is needed for this loop. Studio uses this path for fast previews and can add a second simulated player for testing.

Write to the shared game API rather than browser globals or Node built-ins. Local and hosted execution have different environments: local platform services are empty, while hosted games receive the services the server provides. Local preview alone does not prove that a game will run on a server or pass publishing checks.

Hosted sessions

Homenames, the session-management HTTP service in homegames-core, creates and lists sessions. The shared session manager allocates a port and starts the game in Docker when available. Running it as a plain child process requires the host to enable the fork option. Players connect directly to that session's WebSocket; the website API is not forwarding every game frame.

Game logic runs on the host, but authors still need to validate moves: check whose turn it is, whether a player owns the affected object, and whether an action is allowed. Centralized game state does not make arbitrary client input trustworthy.

Accounts and Studio

Guest Studio work is a browser draft. Sign up with a display name, email, and password, verify the emailed code, then use Save Version to store it in your account. Creation, saving, restoring, uploads, and publishing are verification-gated. Logging in accepts your display name or email. Use the login screen's password-reset flow if needed.

A saved version and a published version are different. Saving writes to Git history; publishing submits a selected commit to validation. A multi-file save currently writes files sequentially and may produce several commits, so select the final successful version when publishing. Archiving a game hides it from your main Studio list; it does not unpublish versions from the public catalog.

Studio offers AI editing in its interface, but the server must separately enable it and have a working background worker. When available, an AI edit is a queued job that saves a new version; review and test it before publishing. The docs question box is a separate service and may be disabled or busy independently. Its answers are generated guidance, not a live inspection of your game.

Publishing and content checks

A verified author submits a saved commit with a game description, thumbnail, substantive README, and changes beyond the starter template. The publishing worker checks metadata, the GPLv3 license text, repository size, and JavaScript imports and operations. It then starts a Docker validation run with networking disabled, serializes the scene, and exercises sample player joins, input, ticks, and disconnects.

A passing commit becomes a published version and makes the game eligible for catalog listings. Featured placement is chosen separately by an administrator. Automated checks are a short smoke test; authors still need to test the game's rules, long-running behavior, controls, and multiplayer experience. See the publishing checklist.

The catalog hides games flagged as NSFW unless its filter includes them. Image uploads are classified when the classifier is available; this is not a guarantee that every upload has been reviewed. An asset's Publish to catalog setting controls discovery, not download permissions: assets are retrievable by ID even when unlisted.

Published game submissions must include GPLv3 license text. Platform repositories have their own license files and package metadata; check the specific repository when reusing code.

Homegames on your network

One computer runs the dashboard and shared sessions. Other devices open that computer's LAN address and game port. The current downloadable server bundle uses http://<server LAN IP>:7001 and leaves link discovery and HTTPS off initially.

  • Discovery: when enabled, your server registers its LAN address and port with homegames.link over an outbound WebSocket. The service matches visitors and servers by their observed public IP, then redirects the browser to the LAN server.
  • HTTPS: when enabled, the server generates its TLS key locally and sends a certificate signing request to the API. A background job obtains a certificate for the network's homegames.link hostname. The hostname points at the private LAN address.
  • Connectivity: discovery is not a tunnel or relay. Friends outside your LAN cannot reach a private address merely because they have its link. Use a hosted website session for ordinary internet play.

Game WebSocket traffic goes directly between the LAN devices and your server. Discovery, certificate issuance, catalog browsing, uncached asset downloads, and configured error reporting can still contact online services. Offline play requires the necessary game files and assets to be available locally.

Follow the self-hosting guide for downloads, explicit configuration, firewall ports, backups, and troubleshooting.
