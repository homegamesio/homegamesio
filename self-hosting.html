Self-hosting Homegames

Run the game dashboard and shared sessions on one computer. Other devices play through their browsers over your local network. A developer account is not required for the home dashboard.

What you get

The server includes a dashboard, built-in games, a browser client, and session management. You can browse the online catalog and install published games, join running sessions, or use browser-local solo play for installed games. This does not install your own copy of the public website, Developer Studio, or account and publishing services.

The launcher supervises homegames-core; shared game sessions run in separate processes or Docker containers. Keep the server computer awake and the launcher running while others play. Closing a player's browser is different from stopping the server.

Start with the LAN address. For the downloadable bundle, open http://localhost:7001 on the server or http://<server LAN IP>:7001 on another device. On a phone, localhost means the phone, not your server. homegames.link is an optional discovery service, and is off in the bundle until enabled.

Download a server bundle

The bundle contains Homegames source, dependencies, Node runtimes, and prefetched game assets. You do not need to install Node, Git, or Docker to launch a supported bundle. This is different from a game page's Download button, which produces one solo HTML game.

⤓ Download Homegames  ·  Windows / macOS / Linux

Extract the entire archive before launching; keep its folders together.

The current builder does not include a Linux ARM runtime. For a Raspberry Pi or another architecture, use a compatible source installation instead of the Linux x64 launcher.

The launcher opens a browser when the server responds. If that does not happen, read its terminal output and open the address manually. On a headless source install, use node index.js --no-open to suppress the browser launch.

The bundle enables child-process sessions when Docker is unavailable. These run game code with the host user's permissions rather than Docker isolation. If Docker and the runner image are available, the session manager still prefers Docker.

    What needs to be available

    • A supported computer that stays awake, a writable application-data directory, and browsers able to reach it over the LAN.
    • For source installs: Git, Node.js, and npm. The bundle builder currently uses Node 24; use that major version when reproducing its environment. The source repos do not declare one consistent minimum Node version.
    • For isolated shared sessions: a running Docker daemon and a built homegames-runner image. Browser-local solo play does not need Docker.
    • Internet for initial dependency installation, catalog downloads, uncached assets, link discovery, and certificate requests. Offline play needs the game's files and assets already present; the catalog itself remains an online service.

    Run from source

    The local packages use sibling file: dependencies. Clone them into one parent directory and install the shared library before its consumers:

    mkdir homegames-server
cd homegames-server
git clone https://github.com/homegamesio/homepad
git clone https://github.com/homegamesio/homegames-common
git clone https://github.com/homegamesio/homegames-client
git clone https://github.com/homegamesio/homegames-core
git clone https://github.com/homegamesio/homegames

cd homepad
npm install
cd ../homegames-common
npm install
cd ../homegames-client
npm install
npm run build
cd ../homegames-core
npm install
cd ../homegames
npm install

    Stop if any install or build fails. The client bundle must exist at homegames-client/dist/homegames-client.js before serving the dashboard. Squish versions are installed by homegames-common; cloning the Squish source alone does not replace those packages. If the client reports a missing squish-NNN, check its src/squish-map.js against common's game-loader.js and dependencies: those lists must agree for a clean build.

    Create homegames-core/config.json with an explicit starting configuration. This avoids inheriting older library defaults:

    {
    "HOME_PORT": 7001,
    "HOMENAMES_PORT": 7100,
    "GAME_SERVER_PORT_RANGE_MIN": 7002,
    "GAME_SERVER_PORT_RANGE_MAX": 7099,
    "LINK_ENABLED": false,
    "HTTPS_ENABLED": false,
    "FORK_SESSIONS_ENABLED": false,
    "ERROR_REPORTING": false,
    "MAP_ENABLED": false,
    "TESTS_ENABLED": false,
    "SAVE_FILES_ENABLED": true
}

    For Docker sessions, build the runner from homegames-core/docker with ./build-image.sh. If you choose to run without Docker, set FORK_SESSIONS_ENABLED to true or turn on Allow fork for child sessions in dashboard settings. This permits unisolated game execution; it does not force Docker off.

    # From the homegames launcher directory:
node index.js

    Open http://localhost:7001. An existing application-data config or environment variable may override the values above; the server logs report the values in use.

    First boot, discovery, and HTTPS

    1. Check that the dashboard loads on the server computer.
    2. Open the server's LAN IP and main port from another device on the same network.
    3. Start a shared session and join it from both devices. This checks the session ports as well as the dashboard port.

    For discovery without HTTPS, set LINK_ENABLED: true in your JSON config and restart. Visit homegames.link from a device using the same public internet connection. The service redirects to your server's LAN IP and port. It does not relay traffic or make that private address accessible from the internet.

    Enable secure connections

    The dashboard calls this Enable multiplayer under the homegames.link settings. It enables discovery and requests a certificate. Ordinary LAN multiplayer can already work over HTTP; this setting adds the secure hostname path.

    1. Choose Enable multiplayer. The server creates a private TLS key and signing request locally. Only the signing request goes to the Homegames API.
    2. Wait for Certificate ready. Issuance depends on the API, background worker, DNS, and certificate authority; it may take several minutes.
    3. Choose Restart to enable homegames.link. The launcher restarts core and opens the link service. This disconnects existing players.

    Use the assigned HTTPS hostname, including its port, once TLS is enabled. A certificate for that hostname does not validate localhost or a raw LAN IP. Until the certificate is installed and the server restarted, the link service may show a setup page.

    Certificates are stored in hg-certs under application data. The manager checks for renewal daily and attempts renewal within 14 days of expiry. Initial HTTPS activation requires restart; an already-running TLS server can reload a renewed certificate.

    Local development and offline use

    To run core directly after installing dependencies and building the client:

    cd homegames-core
npm start

    Use the configured HOME_PORT. Direct execution has no launcher to honor the dashboard's restart requests: after core exits to apply settings, start it again yourself.

    Set START_PATH to a game's directory or index.js to boot straight into it. Relative paths resolve from the running core package directory. Restart to load changed code; npm run develop currently references a missing hotload.js, so it is not the source-start command.

    For offline use, keep discovery, HTTPS provisioning, and error reporting off, and connect by LAN address. The bundle seeds an asset cache from the files it includes. Games or assets downloaded later need to be cached before disconnecting; runtime-created or externally fetched content is not automatically included in the bundle.

    Configuration and ports

    Values resolve in this order: environment variable, user application-data config.json, then the base config found by the running package. If no base file is found, common uses its built-in defaults. Dashboard settings write the user overlay, so those settings survive replacing a downloaded bundle.

    SettingCurrent bundlePurpose
    HOME_PORT7001Dashboard page, browser client, and dashboard WebSocket
    HOMENAMES_PORT7100Session and player management HTTP service
    GAME_SERVER_PORT_RANGE_MIN
    GAME_SERVER_PORT_RANGE_MAX    		7002–7099Inclusive port pool for shared game sessions
    LINK_ENABLEDfalseRegister with homegames.link
    HTTPS_ENABLEDfalseRequest/use a certificate for secure serving
    FORK_SESSIONS_ENABLEDtrueAllow child processes when Docker is unavailable; default without an override is false

    Source defaults differ. With no config file, the common library currently supplies main port 9801, Homenames 7400, session ports 8300–8400, and enables both discovery and HTTPS. Use the explicit configuration above for a predictable first run; do not assume a port or TLS mode from a code comment.

    Use JSON booleans, such as "LINK_ENABLED": false, not the string "false". Port, page-size, and HTTPS changes need a restart. The fork setting is checked for each new session and can take effect immediately.

    Storage, backups, and upgrades

    SystemApplication-data directory
    Windows%APPDATA%\homegames
    macOS~/Library/Application Support/homegames
    Linux~/.homegames

    This contains the user config, certificates, asset cache, and server save data under .save-data. The current dashboard keeps downloaded games under hg-games there. LOCAL_GAME_DIRECTORY can add a separate directory of your own game source; the older DOWNLOADED_GAME_DIRECTORY setting is not consulted by this dashboard path.

    Stop the server before backing up or upgrading. Keep application data and any custom game directories; do not publish backups containing private certificate keys. Extract a new bundle separately and launch it after stopping the old one. Your config overrides persist, so a port or setting from an older installation can still apply. Browser-local saves stay with the player's browser, outside this server backup.

    Firewall and network access

    For the current bundle, allow LAN clients to reach TCP 7001 and the shared session range TCP 7002–7099. Use your configured values if different. Loading the dashboard proves only that the main port is reachable; entering a shared game opens a WebSocket on its allocated session port.

    Homenames is a management service. The implementation listens without a loopback-only bind, so “local API” does not mean the port is automatically private. Keep it restricted to trusted callers. Some management actions require an internal secret, but session creation is not a general authenticated administration interface.

    LAN play needs no internet-facing port forwarding. homegames.link uses an outbound connection and redirects browsers to the LAN address. Guest Wi-Fi, access-point isolation, VPN routing, and networks that share a public IP without sharing LAN connectivity can interfere with discovery or direct connections.

    Troubleshooting

    SymptomCheck
    Nothing at localhostRead the launcher's errors; confirm the actual port and whether the server is serving HTTP or HTTPS. Another installation or a user config may have changed these values.
    Blank dashboard / client script 404Build the sibling browser client and check that dist/homegames-client.js exists. In a bundle, check that the archive was fully extracted.
    “No Homegames servers found”Enable discovery and restart. Check server and browser use the same public connection. Try the LAN IP directly. Hosts without fresh heartbeats drop from discovery after about 90 seconds.
    Certificate ready but setup page remainsChoose the restart button in settings. If running core directly, restart it manually. Check logs for DNS or certificate failures and use the assigned hostname for TLS.
    Dashboard works; shared game will not startCheck Docker is running and homegames-runner is built, or enable the fork option. If Docker started after core, restart core: a failed Docker check can stay cached. Check session logs for unsupported Squish versions, missing assets, and port conflicts.
    Game starts on server, fails on phoneAllow the configured session port range, check Wi-Fi client isolation, and use the server's LAN IP rather than localhost.
    Installed game fails without internetIts source may be installed while an asset is still missing from the cache. Load it online first; games depending on online services cannot become fully offline merely by installing source.
    Game edits do not appear in DockerRebuild the runner image after changing code or dependencies baked into it, then start a new session.
    Progress vanishedCheck that the game implements saving, whether it ran in the browser or on the server, and which version was played. Restarting a session alone does not guarantee a save exists or is compatible.

    Hosting the public services too

    A home game server is only part of the product. A complete independent platform also needs the homegamesio website, API, MongoDB, Forgejo, RabbitMQ, a publishing worker with Docker validation, and a built browser-client bundle for downloads. Email delivery supports verification and password resets. The other worker supplies optional AI/docs jobs and certificate issuance; discovery and certificates require DNS and domain configuration.

    The website currently embeds Homegames service URLs in several entry points, so changing one server-side config value does not redirect the whole site to your infrastructure. Start with the service map and each repository's configuration code. There is no single complete-platform installer in the server bundle.

    For help, include your installation type, OS, configured ports, and the relevant error without passwords or certificate keys. Email joseph@homegames.io.
